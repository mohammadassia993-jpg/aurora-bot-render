## FINDING 1: Missing MAX_DEADLINE Enforcement in Withdrawal.sol AML Signatures
**Severity:** Medium
**Contract:** `Withdrawal.sol`
**Impact:** Extended signature validity window increases attack surface

### Description
NuvaVault.sol enforces `MAX_DEADLINE = 24 hours` for all AML signatures:
```solidity
if (_deadline > block.timestamp + MAX_DEADLINE) revert AmlDeadlineTooLong();
```

However, Withdrawal.sol (the withdrawal counterpart) does NOT enforce this check. The AML signature only requires `block.timestamp > _deadline` to be false, but has no upper bound on how far in the future `_deadline` can be.

### Impact
- If an AML signer signs a message with a 1-year deadline, the signature remains valid for 1 year
- If the AML signer key is later compromised, the attacker could hold the pre-signed message and execute it at an opportune time
- Inconsistent security policy between NuvaVault (24h) and Withdrawal (unlimited)

### Recommendation
Add `MAX_DEADLINE` enforcement to Withdrawal.sol:
```solidity
uint256 public constant MAX_DEADLINE = 24 hours;

function _verifyAML(...) private {
    if (block.timestamp > _deadline) revert AmlSignatureExpired();
    if (_deadline > block.timestamp + MAX_DEADLINE) revert AmlDeadlineTooLong();
    // ...
}
```

## FINDING 2: Non-Standard EIP-712 Type Hash in CrossChainManager
**Severity:** Low
**Contract:** `CrossChainManager.sol`
**Impact:** Potential signature incompatibility with standard EIP-712 tools

### Description
The `_getDepositMessageHash` function concatenates all struct type definitions (Deposit + ExecutorArgs + FeeArgs) into a single type hash string:
```
"Deposit(...)...ExecutorArgs(...)FeeArgs(...)"
```

Per EIP-712 specification, only the primary type should be included in the type hash. Nested struct types should use separate type hashes via `hashStruct()`. While this implementation is internally consistent (signatures from the AML signer will match), it deviates from the standard.

### Impact
- AML signatures generated by external tools following strict EIP-712 will not match
- Any migration to standard EIP-712 verification would break existing signatures

### Recommendation
Separate the primary type hash from dependency type hashes per EIP-712 spec.

## FINDING 3: Silent Permit Failure in NuvaVault.redeemWithPermit
**Severity:** Low
**Contract:** `NuvaVault.sol`
**Impact:** Confusing user experience when allowance is insufficient

### Description
The `redeemWithPermit` function catches permit failures silently:
```solidity
try IERC20Permit(address(this)).permit(...) {} catch {
    // Permit failed or not supported, proceeding with existing allowance
}
```

If the permit fails (e.g., front-run, wrong parameters), the function proceeds to `super.redeem()` which will revert with "ERC4626: allowance too low". The user receives a confusing error that doesn't mention the permit failure.

### Recommendation
Add a flag to track permit success and emit an event or revert with a specific error when both permit and allowance are insufficient.
